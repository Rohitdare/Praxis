# ADR-003: Client-Generated UUIDv4 Primary Keys for Outbox and RPC Synchronization

## Status
Accepted

## Context
- **Problem**: When creating items locally or invoking PostgreSQL stored procedures (such as `classify_and_update_item`), relying on database auto-incrementing IDs or serial sequences breaks offline capture and makes optimistic caching impossible. How should primary keys be generated?
- **Constraints**: Offline-first capture, stable idempotency keys for retries, opaque identifiers, zero coordination latency.

## Options Considered

| Option | Pros | Cons | Complexity | When Valid |
|--------|------|------|------------|------------|
| **Option A: Database Auto-Increment (BIGSERIAL/IDENTITY)** | Compact, sorted | Fails offline; cannot know ID before server roundtrip; outbox cannot reference relational children | Low | Pure online server-rendered apps |
| **Option B: Client-Generated UUIDv4 (`crypto.randomUUID()`)** | Universally unique, zero server roundtrip needed, offline-safe, retry-safe, opaque | 16-byte storage, random B-tree fragmentation if unindexed | Low | Local-first and distributed apps |
| **Option C: ULID / UUIDv7** | Time-ordered, monotonic | Requires extra client library dependency | Low-Medium | High-throughput write-heavy tables |

## Decision
**Chosen**: Option B — Client-Generated UUIDv4.
Primary keys for `items`, `tasks`, `calendar_events`, and `resources` are generated by the client using native `crypto.randomUUID()`. Stored procedures accept client-provided item IDs (`p_item_id UUID`), and RPC calls reuse stable IDs across retries.

## Rationale
1. **Zero Coordination**: The client can create an item in Dexie IndexedDB, attach child metadata, and display it in UI immediately without waiting for server network response.
2. **Idempotent Retries**: If network drops mid-request, retrying the create/update with the identical client-generated UUID prevents duplicate record insertion.
3. **No External Libraries**: Supported natively in modern browsers and Web Workers via `crypto.randomUUID()`.

## Trade-offs Accepted
- Slight storage overhead compared to 8-byte integers.
- Timestamps (`created_at`, `captured_at`) must be indexed for chronological ordering rather than relying on ID ordering.

## Consequences
- **Positive**: Immediate optimistic rendering; bulletproof outbox queue; safe retries across network flakiness.
- **Negative**: Must validate UUID format on server functions.
- **Mitigation**: Database migration enforces `id UUID PRIMARY KEY DEFAULT gen_random_uuid()` with NOT NULL constraints.

## Revisit Trigger
- If high write volume exceeds millions of records per day and index fragmentation warrants migration to UUIDv7.
